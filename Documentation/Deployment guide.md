# 🚀 Deployment Guide

## 🗺️ How This Works

User intervention is kept to a minimum. There are three tiers of automation:

| Tier | Who does it | When |
|---|---|---|
| **One-time bootstrap** | You, manually | Once, to wire up CI |
| **Infrastructure deploy** | GitHub Actions CI | Push to `main` deploys dev; push to `prod` branch deploys prod |
| **Application changes** | Flux (automatic) | Every 60 seconds, continuously |

After the bootstrap, the normal workflow is: **open a PR → merge to `main` → CI deploys to dev → push to `prod` branch when ready for production**. You never run Terraform or Ansible manually again.

---

## ✅ What Is Genuinely Manual vs Automated

| Step | Why |
|---|---|
| `gcloud auth login` | A human must authenticate before anything else can run |
| `gh auth login` | GitHub CLI must be authenticated before running the bootstrap script |
| Everything else | Run `scripts/bootstrap.sh` — it handles the rest automatically |

The bootstrap script automates: state bucket creation, SSH key generation, `terraform.tfvars` population, `terraform apply` on the bootstrap module, and setting `SSH_PRIVATE_KEY` in GitHub secrets via the `gh` CLI (the private key never passes through Terraform state).

After the script completes, pushing any change touching `terraform/`, `ansible/`, `gitops/`, or `.github/workflows/` to `main` will trigger CI and deploy to dev automatically. Pushing to the `prod` branch deploys to prod.

Postgres and Grafana passwords are auto-generated by Terraform's `random_password` resource and written directly to Secret Manager. They are never seen or entered by a human. 🔐

## 🔧 Part 1 — One-Time Bootstrap

### 📋 Prerequisites

You need the following tools installed locally:

| Tool | Required for | Install |
|---|---|---|
| `gcloud` CLI | GCP authentication | https://cloud.google.com/sdk/docs/install |
| Terraform | Running the bootstrap module | https://developer.hashicorp.com/terraform/install |
| `gh` CLI | GitHub authentication, setting secrets | https://cli.github.com |
| `kubectl` | Verifying the cluster (Part 3) | https://kubernetes.io/docs/tasks/tools |

Ansible is not needed locally — CI runs it.

You also need:

- A **GCP account** with billing enabled
- A **GCP project** — create at https://console.cloud.google.com/projectcreate or use an existing one

---

### 1.1 🔐 Authenticate

```bash
# GCP
gcloud auth login
gcloud auth application-default login
gcloud config set project <your-project-id>

# GitHub CLI
gh auth login
```

---

### 1.2 📥 Clone the Repository

```bash
git clone https://github.com/<your-github-username>/enclaive-platform-challenge
cd enclaive-platform-challenge
```

> **Note:** The `github_owner` used for Flux bootstrap is derived automatically from `github.repository_owner` in CI — no hardcoding needed. If you fork this repo, CI picks up your username automatically.

---

### 1.3 🚀 Run the Bootstrap Script

The bootstrap script handles everything else automatically:

```bash
bash scripts/bootstrap.sh
```

What it does:

1. Creates the Terraform state bucket in GCS
2. Generates an SSH key pair at `~/.ssh/enclaive-ci`
3. Writes `terraform/bootstrap/terraform.tfvars` (gitignored)
4. Runs `terraform apply` on the bootstrap module — creates the CI identity, Workload Identity Federation, and populates all GitHub Actions secrets
5. Sets `SSH_PRIVATE_KEY` in GitHub secrets via `gh secret set` — the private key never passes through Terraform state
6. Prompts you to create and paste a **fine-grained Personal Access Token** for Flux, then sets it as `FLUX_GITHUB_TOKEN` in GitHub secrets

> **Why a separate token for Flux?** Flux runs inside the cluster and polls the repository every 60 seconds indefinitely. The `GITHUB_TOKEN` CI provides is ephemeral and expires the moment each run ends — Flux would lose access to Git immediately. `FLUX_GITHUB_TOKEN` is a long-lived PAT that persists across runs. When prompted by the script, create one at **GitHub → Settings → Developer settings → Personal access tokens → Fine-grained tokens** with `Contents: Read-only` for this repository.

**Optional overrides** (set as env vars before running):

```bash
REGION=europe-west1          # GCP region
ADMIN_CIDR=203.0.113.10/32  # your IP for k8s API access (auto-detected if not set)
bash scripts/bootstrap.sh
```

The script is idempotent — safe to re-run if it fails partway through. ✅

## 🚢 Part 2 — Deploy

With the bootstrap complete, deploying follows the branch:

- **dev** — push any change touching `terraform/`, `ansible/`, `gitops/`, or `.github/workflows/` to `main`
- **prod** — push the same change to the `prod` branch
- **manual** — use the `workflow_dispatch` trigger in GitHub → Actions → Deploy → Run workflow; select the target environment from the dropdown (useful for re-running Ansible without a code change, e.g. after a ConfigMap fix)

### 2.1 🎯 Trigger the First Deploy

1. Open a PR with your infrastructure changes and get it reviewed. The CI pipeline validates on every PR:
   - Secret scanning, YAML lint, markdown lint (all PRs)
   - `terraform fmt`, `terraform validate`, `terraform plan` for both `dev` and `prod` (when `terraform/` changes)
   - `ansible-lint`, `kubeconform` (when relevant paths change)

2. Merge the PR to `main`. CI triggers automatically and will:
   - **Apply** — `terraform apply` provisions all GCP infrastructure; passwords are auto-generated and stored in Secret Manager
   - **Bootstrap** — `ansible-playbook bootstrap.yml` installs k3s and Flux on the nodes; inventory is built dynamically from GCP labels — no static file needed
   - **Post-deploy verification** (`post-deploy-checks.yml`) — waits for Flux convergence and Postgres bootstrap, then asserts nodes are Ready, all kustomizations reconciled, Postgres cluster healthy, Adminer reachable

3. When ready to deploy to prod, push the relevant commits to the `prod` branch. The same pipeline runs, targeting the prod environment and the prod Flux entry point (`gitops/clusters/prod/`).

Monitor the run in **GitHub → Actions**. Total CI time is approximately 15–20 minutes (Flux reconciles kube-prometheus-stack which takes up to 15 minutes on first install).

### 2.2 ⏳ After CI Completes

When the CI job finishes, Flux is running inside the cluster and has already begun reconciling `gitops/`. From this point, all changes to the cluster happen through Git — no CI jobs needed for application or configuration changes.

## ✅ Part 3 — Verify

The Ansible playbook fetches the kubeconfig from the control plane and uploads it as a CI job artifact with the server address already patched to the external IP.

### 3.0 🔑 Get the Kubeconfig

1. Go to your repository on GitHub → **Actions**
2. Click the completed deploy run
3. Scroll to **Artifacts** at the bottom of the run page
4. Download `kubeconfig-enclaive-<environment>` and save it to `~/.kube/config-enclaive-<environment>`

Then point kubectl at it:

```bash
export KUBECONFIG=~/.kube/config-enclaive-<environment>
```

> The API server (port 6443) is restricted to your `ADMIN_CIDR` by the GCP firewall. If kubectl times out, confirm your current IP matches the CIDR you used during bootstrap.

### 3.1 🖥️ Check the Cluster

```bash
kubectl get nodes
```

Expected output:

```text
NAME                STATUS   ROLES                  AGE   VERSION
<env>-node-01      Ready    control-plane,master   5m    v1.35.3+k3s1
<env>-node-02      Ready    <none>                 4m    v1.35.3+k3s1
<env>-node-03      Ready    <none>                 4m    v1.35.3+k3s1
```

### 3.2 🔄 Watch Flux Reconcile

```bash
flux get kustomizations -A --watch
```

Wait until all kustomizations show `True` in the Ready column. The order is: `common` (HelmReleases) → `eso-config` (secrets) → `postgres` and `monitoring` in parallel → `demo-app`. `common` typically takes 5–10 minutes on first install; `monitoring` (kube-prometheus-stack) can take up to 15 minutes but runs in parallel and doesn't block the application. If a kustomization stays in a failed state:

```bash
flux logs --kind=Kustomization --name=<name> -n flux-system
```

### 3.3 🐘 Verify PostgreSQL

```bash
kubectl get cluster -n postgres
kubectl get pods -n postgres
```

The cluster status should show `Cluster in healthy state`. All three pods (`pg-1`, `pg-2`, `pg-3`) should be `Running`.

### 3.4 📊 Access Grafana

Grafana is exposed through ingress-nginx at the same node IP as Adminer (use the node where `kubectl get pod -n ingress-nginx -o wide` shows the pod running):

```text
http://<ingress-node-external-ip>/grafana
```

Retrieve the admin password from Secret Manager:

```bash
gcloud secrets versions access latest --secret=<environment>-grafana-admin-password
```

Log in as **admin** with that password. Navigate to **Dashboards → CloudNativePG** for PostgreSQL metrics.

### 3.5 🖥️ Access Adminer

Adminer is reachable directly in the browser — no port-forwarding needed. ingress-nginx uses `hostPort` mode, binding ports 80 and 443 on whichever node(s) its pod is scheduled on (see [Architecture → Ingress and Load Balancing](Architecture.md#-ingress-and-load-balancing)). First check which node has the pod:

```bash
kubectl get pod -n ingress-nginx -o wide
```

Then use the external IP of that node:

```text
http://<ingress-node-external-ip>/adminer
```

Get the node's external IP with:

```bash
gcloud compute instances list \
  --project=<your-project-id> \
  --filter="labels.environment=<environment>" \
  --format="table(name, networkInterfaces[0].accessConfigs[0].natIP, labels.role)"
```

Retrieve the app user password from Secret Manager:

```bash
gcloud secrets versions access latest \
  --secret=<environment>-pg-app-password \
  --project=<your-project-id>
```

Connect with:

| Field | Value |
|---|---|
| System | PostgreSQL |
| Server | `pg-rw.postgres.svc.cluster.local` |
| Username | `app` |
| Password | _(output of the gcloud command above)_ |
| Database | `app` |

### 3.6 ✅ Verify the Database End-to-End

Once logged in, click **SQL command** in the left sidebar and run:

```sql
CREATE TABLE greetings (
  id   SERIAL PRIMARY KEY,
  msg  TEXT NOT NULL,
  ts   TIMESTAMPTZ DEFAULT now()
);

INSERT INTO greetings (msg) VALUES ('Hello from the platform!');

SELECT * FROM greetings;
```

A row returned confirms writes and reads work on the primary.

To verify streaming replication to both replicas is active:

```sql
SELECT application_name, state, sent_lsn, write_lsn, replay_lsn
FROM pg_stat_replication;
```

You should see two rows (one for each replica) with `state = streaming`. This confirms the full HA stack is working end-to-end.

## 🗓️ Part 4 — Day-to-Day Operations

**For application or cluster config changes** (anything under `gitops/`):

1. Edit the file
2. Push to a branch, open a PR
3. Merge — Flux picks up the change within 60 seconds — no CI run needed

**For infrastructure changes** (anything under `terraform/` or `ansible/`):

1. Edit the file
2. Push to a branch, open a PR — CI runs `terraform plan` so you can review the impact before merging
3. Merge — CI runs `terraform apply` and Ansible if needed

> ⚠️ Never run `kubectl apply` directly. Any manual change will be overwritten by Flux on the next reconcile.

For upgrade procedures (Postgres, k3s, Flux) and scaling operations, see [Operational Lifecycle](Operational%20lifecycle.md).

## 💣 Teardown

```bash
cd terraform/environments/<environment>
terraform destroy
```

Type `yes` when prompted. The GCS backup bucket is deleted automatically (`force_destroy = true`). The Terraform **state bucket** is not managed by Terraform — delete it manually:

```bash
gcloud storage rm -r gs://${PROJECT_ID}-tfstate
```

The bootstrap state lives in the same GCS bucket under the `bootstrap` prefix and will be cleaned up when the bucket is deleted.

## 🔧 Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| Bootstrap `terraform apply` fails with permission error | ADC not set or wrong project | Re-run step 1.1 |
| CI fails with WIF authentication error | WIF provider not configured | Re-run bootstrap `terraform apply` |
| CI fails at `ansible-playbook` | SSH key mismatch | Confirm `SSH_PRIVATE_KEY` secret matches `~/.ssh/enclaive-ci` |
| Node not `Ready` | k3s failed to start | SSH into node: `sudo systemctl status k3s` or `sudo systemctl status k3s-agent` |
| `common` kustomization stuck | HelmRelease install slow on first run | Check: `flux logs --kind=Kustomization --name=common -n flux-system` and `kubectl get helmrelease -A` |
| `eso-config` kustomization stuck | ESO not yet running or CRD missing | Wait for `common` first; check ESO pod: `kubectl get pods -n external-secrets` |
| `eso-config` fails with "no matches for ExternalSecret" | ESO manifests must use `external-secrets.io/v1`, not `v1beta1` | ESO 0.9+ promoted the API — `v1beta1` is no longer served |
| `postgres` kustomization stuck | Depends on `eso-config` — wait for it | Check: `flux logs --kind=Kustomization --name=postgres -n flux-system` |
| `monitoring` kustomization slow | kube-prometheus-stack can take 15 min | Normal — it runs in parallel and doesn't block the app. Check: `kubectl get helmrelease -n monitoring` |
| Flux GitRepository shows "Invalid username or token" | `FLUX_GITHUB_TOKEN` secret missing or expired | Regenerate the PAT and re-set the secret: `gh secret set FLUX_GITHUB_TOKEN`; update the in-cluster secret with `kubectl patch secret flux-system -n flux-system` |
| CNPG Cluster CR rejected by webhook | `gkeEnvironment: false` requires an explicit SA key secret | Cluster CR uses `gkeEnvironment: true` — the node SA accesses GCS via the metadata server; no key file needed |
| WAL archiving fails: `Project was not passed` | `GOOGLE_CLOUD_PROJECT` env var not set in Postgres pods | Verify the Cluster CR has `spec.env: [{name: GOOGLE_CLOUD_PROJECT, value: ...}]` and that Flux has reconciled it |
| WAL archiving fails: `metadata.google.internal` unreachable | CoreDNS not patched — Flannel pods cannot resolve GCE internal DNS hostnames | Check `kubectl get configmap coredns -n kube-system -o yaml` contains `169.254.169.254 metadata.google.internal` in `NodeHosts`; if missing, re-run Ansible or patch manually |
| WAL archiving fails: `403 storage.buckets.get access denied` | Node SA missing `roles/storage.legacyBucketReader` on the backup bucket | Run `terraform apply` — the gcs module now grants both `objectAdmin` and `legacyBucketReader`; or add the role manually via `gcloud storage buckets add-iam-policy-binding` |
| Adminer not reachable in browser | ingress-nginx pod not on that node | Check which nodes have the pod: `kubectl get pod -n ingress-nginx -o wide`; use that node's external IP |
| kubectl connection refused or times out | API server port (6443) firewalled | Confirm your current IP matches `ADMIN_CIDR` used during bootstrap |
| kubeconfig artifact empty | scp step failed | SSH to control plane manually: `scp ubuntu@<cp-ip>:/etc/rancher/k3s/k3s.yaml ~/.kube/config-enclaive-<environment>` |
| Cannot retrieve app password | Secret Manager access | Run `gcloud secrets versions access latest --secret=<environment>-pg-app-password` |
