# 🏗️ Terraform

This directory provisions all the cloud infrastructure on **Google Cloud Platform** that the platform runs on. Terraform is responsible for everything from VMs to networking to IAM — but nothing above the OS level. Once it outputs a list of IP addresses, its job is done and Ansible takes over.

## 🧱 What gets provisioned

- 🖥️ **3 GCE virtual machines** — one control plane node, two workers, all running Ubuntu 24.04 LTS
- 🌐 **VPC and subnet** — isolated network at `10.0.0.0/24`
- 🔥 **Firewall rules** — SSH and Kubernetes API restricted to your IP only; internal cluster traffic open
- 📌 **Static internal IPs** — reserved per node, mandatory for k3s stability (node identity breaks if IPs change)
- 🪣 **GCS backup bucket** — used by CloudNativePG for WAL archiving and base backups
- 🤖 **Node service account** — least-privilege GCP service account attached to the VMs; used by ESO and CNPG to access GCP APIs without storing credentials
- 🔐 **Passwords** — Postgres and Grafana admin passwords are auto-generated by `random_password` and stored directly in Secret Manager; never entered or seen by a human

## 📁 Structure

```
terraform/
  bootstrap/          ← run once, manually, before CI exists
  modules/
    network/          ← VPC + subnet
    node/             ← single GCE VM + reserved static internal IP
    firewall/         ← SSH, k8s API, ingress, internal traffic rules
    gcs/              ← CloudNativePG backup bucket
    iam/              ← node service account + IAM bindings
  environments/
    dev/              ← wires modules together; e2-standard-2, 30-day backup retention
    prod/             ← same modules; e2-standard-4, 90-day backup retention
```

Modules are reusable building blocks — `environments/dev` and `environments/prod` both call the same modules with different inputs. Adding a new environment means creating a new directory under `environments/` and passing different variables. No module code changes needed. 🎉

## 🔑 The bootstrap module

Before CI can run Terraform, something has to create the CI identity itself — this is the bootstrap chicken-and-egg problem. The `bootstrap/` module solves it by running **once** with your personal GCP credentials:

- ✅ Enables all required GCP APIs
- 🤖 Creates the CI service account with least-privilege IAM roles (no `roles/editor`)
- 🔐 Sets up Workload Identity Federation so GitHub Actions authenticates to GCP without storing any credentials
- 🔒 Populates all non-sensitive GitHub Actions secrets automatically

After bootstrap you never touch this module again. See the [Deployment Guide](../Documentation/deployment-guide.md) for the full walkthrough.

## 🧠 Key design decisions

**📌 Static internal IPs** — k3s bakes node identity into certificates and etcd membership at bootstrap time. A dynamic IP that changes on VM restart would silently break the cluster. Every node gets a `google_compute_address` resource with `address_type = INTERNAL`.

**🚫 No `roles/editor` on CI** — the CI service account has only the specific IAM roles it needs (`compute.admin`, `secretmanager.admin`, etc.). `roles/editor` is a common shortcut that grants far too much access.

**🔐 Workload Identity Federation** — CI authenticates to GCP using short-lived OIDC tokens issued by GitHub, not a long-lived service account key stored as a secret. No credentials to rotate, no credentials to leak.

**🎲 `random_password` for Postgres** — credentials are generated by Terraform, written straight to Secret Manager, and never stored anywhere a human can read them. The state bucket is GCS with uniform bucket-level access and IAM-restricted.

**💥 `force_destroy = true` on the backup bucket** — GCP refuses to delete non-empty buckets. Without this flag, `terraform destroy` would always fail and require manual cleanup.

## 🌍 Environments

| | dev | prod |
|---|---|---|
| Machine type | `e2-standard-2` | `e2-standard-4` |
| Backup retention | 30 days | 90 days |
| Subnet | `10.0.0.0/24` | `10.1.0.0/24` |

Both environments live in the same GCP project and use the same Terraform state bucket (under different prefixes: `environments/dev`, `environments/prod`).

## 🚦 How CI uses Terraform

CI runs Terraform automatically on every merge to `main` that touches `terraform/`. You never run `terraform apply` manually after the initial bootstrap. On pull requests, CI runs `terraform plan` so you can review the impact before merging.

For the full picture of how Terraform fits into the CI pipeline, see the [Technical Analysis](../Documentation/technical-analysis.md).
