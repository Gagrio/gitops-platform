# Deployment Guide

## How This Works

User intervention is kept to a minimum. There are three tiers of automation:

| Tier | Who does it | When |
|---|---|---|
| **One-time bootstrap** | You, manually | Once, to wire up CI |
| **Infrastructure deploy** | GitHub Actions CI | On every merge to `main` touching `terraform/` or `ansible/` |
| **Application changes** | Flux (automatic) | Every 60 seconds, continuously |

After the bootstrap, the normal workflow is: **open a PR → merge → CI and Flux handle everything**. You never run Terraform or Ansible manually.

---

## What Is Genuinely Manual vs Automated

| Step | Why |
|---|---|
| `gcloud auth login` | A human must authenticate before anything else can run |
| Create Terraform state bucket | Cannot use Terraform to create its own backend — bootstrap problem |
| Generate SSH key pair | Private key must never enter Terraform state — generated externally and stored directly in GitHub secrets |
| Add `SSH_PRIVATE_KEY` to GitHub | Only secret entered manually — all others are set by the bootstrap Terraform |
| `terraform apply` (bootstrap only) | Runs once locally to create CI identity and populate GitHub secrets |
| Everything else | Fully automated — CI runs Terraform and Ansible, Flux handles the cluster |

Postgres passwords are auto-generated by Terraform's `random_password` resource and written directly to Secret Manager. They are never seen or entered by a human.

## Part 1 — One-Time Bootstrap

### Prerequisites

You need the following tools installed locally for the bootstrap and verification steps:

| Tool | Required for | Install |
|---|---|---|
| `gcloud` CLI | GCP authentication, state bucket creation | https://cloud.google.com/sdk/docs/install |
| Terraform | Running the bootstrap module | https://developer.hashicorp.com/terraform/install |
| `kubectl` | Verifying the cluster (Part 3) | https://kubernetes.io/docs/tasks/tools |
| `flux` CLI | Verifying GitOps reconciliation (Part 3) | https://fluxcd.io/flux/installation/#install-the-flux-cli |

Ansible is not needed locally — CI runs it.

You also need:
- A **GCP account** with billing enabled — https://console.cloud.google.com
- A **GCP project** — create one at https://console.cloud.google.com/projectcreate or use an existing one
- A **GitHub personal access token** with `repo` scope — create at https://github.com/settings/tokens (click **Generate new token (classic)**, tick `repo`)

---

### 1.1 Authenticate with GCP

```bash
gcloud auth login
gcloud auth application-default login
gcloud config set project <your-project-id>
```

Both commands open a browser window to sign in with your Google account. Find your project ID with `gcloud projects list`.

---

### 1.2 Create the Terraform State Bucket

This is the only resource created outside of Terraform. It must exist before `terraform init` can run. Choose a globally unique name — a good convention is `<project-id>-tfstate`:

```bash
export PROJECT_ID=$(gcloud config get project)
export REGION=europe-west1

gcloud storage buckets create gs://${PROJECT_ID}-tfstate \
  --location=${REGION} \
  --uniform-bucket-level-access
```

---

### 1.3 Generate an SSH Key Pair for CI

CI uses this key to SSH into the nodes and run Ansible. Generate a dedicated key pair — do not reuse a personal key:

```bash
ssh-keygen -t rsa -b 4096 -f ~/.ssh/enclaive-ci -N ""
```

This creates:
- `~/.ssh/enclaive-ci` — the **private key** (you will add this to GitHub secrets manually in step 1.6)
- `~/.ssh/enclaive-ci.pub` — the **public key** (goes into the bootstrap Terraform variables)

The private key is never passed through Terraform — it is the only secret you enter manually. This keeps it out of Terraform state entirely.

---

### 1.4 Configure and Run the Bootstrap Terraform

The bootstrap Terraform module creates everything else automatically:
- Enables all required GCP APIs
- Creates the CI service account with least-privilege IAM roles (no `roles/editor` — only the specific roles Terraform needs)
- Sets up Workload Identity Federation so CI authenticates to GCP without storing credentials
- Populates all non-sensitive GitHub Actions secrets automatically

The bootstrap module uses the same GCS bucket as all other environments, under the `bootstrap` prefix. The bucket already exists from step 1.2, so there is no dependency issue.

```bash
cd terraform/bootstrap
cp terraform.tfvars.example terraform.tfvars
```

Open `terraform.tfvars` and fill in your values:

**`project_id`** — Your GCP project ID:
```bash
gcloud projects list
```

**`region`** — GCP region to deploy into. Default is `europe-west1`. See https://cloud.google.com/compute/docs/regions-zones.

**`github_owner`** — Your GitHub username.

**`github_repo`** — Leave as `enclaive-platform-challenge` unless you renamed your fork.

**`tf_state_bucket`** — The bucket name you created in step 1.2 (e.g. `your-project-id-tfstate`).

**`admin_cidr`** — Your current public IP in CIDR notation. Find it with:
```bash
curl ifconfig.me
# Append /32, e.g. 203.0.113.10/32
```
This restricts SSH and Kubernetes API access to your machine only.

**`ssh_public_key`** — Contents of the public key from step 1.3:
```bash
cat ~/.ssh/enclaive-ci.pub
```

**`github_token`** — Your GitHub personal access token from the prerequisites step.

Then run:

```bash
terraform init -backend-config="bucket=<your-bucket-name>"
terraform apply
```

Type `yes` when prompted. This takes about 1 minute. When complete, all GitHub Actions secrets are populated automatically.

---

### 1.5 Add the SSH Private Key to GitHub Manually

This is the only secret you enter manually. Go to your repository on GitHub → **Settings → Secrets and variables → Actions → New repository secret**.

Add one secret:

| Name | Value |
|---|---|
| `SSH_PRIVATE_KEY` | Contents of `~/.ssh/enclaive-ci` |

Print the private key to copy it:
```bash
cat ~/.ssh/enclaive-ci
```

Copy the entire output including the `-----BEGIN RSA PRIVATE KEY-----` and `-----END RSA PRIVATE KEY-----` lines.

> This is the only secret that cannot go through Terraform — it would be stored in Terraform state if it did, which is a security risk regardless of where the state lives. All other secrets were set automatically in step 1.4.

## Part 2 — Deploy

With the bootstrap complete, deploying is a single Git operation.

### 2.1 Trigger the First Deploy

Merge any change to `main` that touches `terraform/` or `ansible/`. The CI pipeline will:

1. **Validate** (on PR) — `terraform fmt`, `terraform validate`, `terraform plan`, `ansible-lint`, `kubeconform`
2. **Apply** (on merge) — `terraform apply` provisions all GCP infrastructure; Postgres passwords are auto-generated and stored in Secret Manager
3. **Bootstrap** (on merge) — `ansible-playbook bootstrap.yml` installs k3s and Flux on the nodes

Monitor the run in **GitHub → Actions**. Total CI time is approximately 10–15 minutes.

### 2.2 After CI Completes

When the CI job finishes, Flux is running inside the cluster and has already begun reconciling `gitops/`. From this point, all changes to the cluster happen through Git — no CI jobs needed for application or configuration changes.

## Part 3 — Verify

Retrieve the kubeconfig to connect to the cluster. The Ansible playbook uploads it as a CI job artifact. Download it from the GitHub Actions run:

1. Go to your repository on GitHub → **Actions**
2. Click the completed deploy run
3. Scroll to **Artifacts** at the bottom of the run page
4. Download `kubeconfig-enclaive-dev` and save it to `~/.kube/config-enclaive-dev`

Then point kubectl at it:

```bash
export KUBECONFIG=~/.kube/config-enclaive-dev
```

### 3.1 Check the cluster

```bash
kubectl get nodes
```

Expected output:
```
NAME           STATUS   ROLES                  AGE   VERSION
dev-node-01   Ready    control-plane,master   5m    v1.x.x+k3s1
dev-node-02   Ready    <none>                 4m    v1.x.x+k3s1
dev-node-03   Ready    <none>                 4m    v1.x.x+k3s1
```

### 3.2 Watch Flux reconcile

```bash
flux get kustomizations -A --watch
```

Wait until all kustomizations show `True` in the Ready column. This takes 5–10 minutes after the cluster is up. If a kustomization stays in a failed state:

```bash
flux logs --kind=Kustomization --name=<name> -n flux-system
```

### 3.3 Verify PostgreSQL

```bash
kubectl get cluster -n postgres
kubectl get pods -n postgres
```

The cluster status should show `Cluster in healthy state`. All three pods (`pg-1`, `pg-2`, `pg-3`) should be `Running`.

### 3.4 Access Grafana

```bash
kubectl port-forward svc/kube-prometheus-stack-grafana 3000:80 -n monitoring
```

Open http://localhost:3000. Default credentials: **admin / prom-operator**. Navigate to **Dashboards → CloudNativePG** for PostgreSQL metrics.

### 3.5 Access Adminer

```bash
kubectl port-forward svc/adminer 8080:80 -n demo-app
```

Open http://localhost:8080. Connect with:

| Field | Value |
|---|---|
| System | PostgreSQL |
| Server | `postgres-rw.postgres.svc.cluster.local` |
| Username | `app` |
| Password | Retrieve from Secret Manager: `gcloud secrets versions access latest --secret=dev-pg-app-password` |
| Database | `app` |

A successful login confirms the full stack is working end-to-end.

## Part 4 — Day-to-Day Operations

**For application or cluster config changes** (anything under `gitops/`):
1. Edit the file
2. Push to a branch, open a PR
3. Merge — Flux picks up the change within 60 seconds

**For infrastructure changes** (anything under `terraform/` or `ansible/`):
1. Edit the file
2. Push to a branch, open a PR — CI runs `terraform plan` so you can review the impact before merging
3. Merge — CI runs `terraform apply` and Ansible if needed

> Never run `kubectl apply` directly. Any manual change will be overwritten by Flux on the next reconcile.

## Teardown

```bash
cd terraform/environments/dev
terraform destroy
```

Type `yes` when prompted. The GCS backup bucket is deleted automatically (`force_destroy = true`). The Terraform **state bucket** is not managed by Terraform — delete it manually:

```bash
gcloud storage rm -r gs://${PROJECT_ID}-tfstate
```

The bootstrap state lives in the same GCS bucket under the `bootstrap` prefix and will be cleaned up when the bucket is deleted.

## Troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| Bootstrap `terraform apply` fails with permission error | ADC not set or wrong project | Re-run step 1.1 |
| CI fails with WIF authentication error | WIF not configured correctly | Re-run bootstrap `terraform apply` |
| CI fails at `ansible-playbook` | SSH key mismatch | Confirm `SSH_PRIVATE_KEY` secret matches `~/.ssh/enclaive-ci` |
| Node not `Ready` | k3s failed to start | SSH into node: `sudo systemctl status k3s` |
| Flux kustomization stuck | Image pull slow or dependency not ready | Wait, then check `flux logs --kind=Kustomization --name=<name> -n flux-system` |
| Cannot retrieve app password | Secret Manager access | Run `gcloud secrets versions access latest --secret=dev-pg-app-password` |
